RESEARCH IMPACT ANALYSIS - ADVERSARIAL SEO CODE REFACTORING
Nestaas et al., 2024: "Adversarial Search Engine Optimization for Large Language Models"

===============================================================================
EXECUTIVE SUMMARY
===============================================================================

This refactoring effort transformed the adversarial SEO research codebase from a monolithic structure into a modular, well-architected system while maintaining complete fidelity to the original paper's methodology. The refactoring involved two major phases: data structure unification for benchmark integration and code modularization for improved maintainability. Crucially, all paper findings remain fully reproducible with the refactored code. The 38 percent average position-1 success rate, prisoner's dilemma degradation dynamics, and positional bias effects can all be replicated exactly. The refactoring introduces zero changes to the core experimental logic, attack mechanisms, or evaluation metrics that would alter research outcomes.

The primary motivation was to prepare the codebase for integration with the lab group's benchmark framework while improving code quality for long-term research sustainability. The dataset was restructured from a flat array to a hierarchical category-based format, and the code was decomposed from four monolithic files into twenty-five focused modules organized into packages. All changes were purely structural, with attack mechanisms operating at the string level and remaining completely unchanged. For the research team, this means improved collaboration capabilities, easier extension for future experiments, and better alignment with the lab's existing tools and conventions, all without sacrificing any of the paper's core findings or experimental rigor.


===============================================================================
DATASET UNIFICATION IMPACT
===============================================================================

The dataset restructuring represents the most visible change in the refactored codebase, transforming how product data is organized while preserving all experimental capabilities. Previously, the sixty fictional products existed as a simple flat array where each product was a dictionary with fields like identifier, name, description, category, price, and rating. The new unified structure introduces a hierarchical organization where products are grouped by category under a top-level categories dictionary, with metadata tracking the total product count, category distribution, and format version. This change from flat to hierarchical organization was implemented specifically to align with the lab group's standard dataset format, enabling easier integration with other benchmark experiments and facilitating data sharing across research projects.

For the adversarial SEO research specifically, this restructuring has zero impact on experimental outcomes because attacks operate at the description string level, not on the JSON structure. When attack text is injected into product descriptions using techniques like prompt injection, discreditation, or persuasion, the injection mechanism appends or prepends text to description strings regardless of how those products are organized in the source file. The vector database population process flattens the hierarchical structure back into a simple document list where each product becomes a standalone document with its attacked description. The retrieval-augmented generation pipeline then operates on these flattened documents, meaning the LLM never sees the category structure at all. From the LLM's perspective, nothing has changed about how products are presented or how attacks are embedded within their descriptions.

The hierarchical structure does introduce new capabilities for category-based experiments that were more difficult with the flat format. Researchers can now easily sample products in a stratified manner across categories, ensuring representation from books, cameras, computing hardware, and other product types in test sets. Category-specific attacks can be tested by targeting all products within a category, enabling investigation of domain-specific attack patterns. The structure also supports controlled ordering experiments where products can be arranged by category or alternated across categories to test whether category clustering affects LLM ranking decisions. These are new research opportunities enabled by the restructuring, but they do not alter or invalidate the original paper's findings, which used the full product set without category-based sampling.

The backward compatibility implementation ensures that existing analysis code continues to function without modification. The data loader automatically detects whether it is reading the new unified format, the old flat array format, or several intermediate formats that existed during migration. Regardless of which format is present in the source file, the loader returns a consistent flat list of sixty products that matches what the original code expected. This means notebooks, scripts, and analysis tools that were written for the flat format continue to work seamlessly. The deprecation layer provides warnings to guide future development toward the new format while maintaining full operational compatibility with legacy code patterns.

ALGORITHM AND IMPLEMENTATION CHANGES
===============================================================================

At the algorithmic level, the refactoring introduces no changes that affect research results. The core components of the adversarial SEO methodology remain identical in their fundamental logic. The LLM ranking mechanism still retrieves top-K documents using vector similarity over product descriptions and reranks them using the large language model with the same prompt structure documented in the original experiments. The attack injection process still modifies product descriptions by appending or prepending adversarial text before those descriptions are embedded into the vector database. The evaluation metrics still measure success rates by comparing baseline rankings to attacked rankings and checking whether the attacked product moved to position one.

The statistical analysis methods remain unchanged. T-tests for comparing success rates across attack types use the same scipy functions with identical parameters. Analysis of variance for prisoner's dilemma experiments uses the same statistical framework. Confidence interval calculations follow the same mathematical definitions. The positional bias analysis compares attack effectiveness across document positions using the same position-aware evaluation logic. All of these statistical methods produce identical numerical outputs when given the same experimental data, meaning paper findings remain exactly reproducible.

The modularization did introduce abstraction layers that separate concerns more cleanly than the original monolithic code. The ranking mechanism was decomposed into separate retrieval and generation stages, with the retriever handling vector search and the generator handling LLM interaction. This separation makes no algorithmic changes to either stage but does make the code easier to test and modify. If a researcher wants to experiment with different retrieval strategies or swap LLM providers, they can now do so by implementing new strategy classes rather than editing a large monolithic function. The experiment framework was similarly decomposed into a base experiment class that defines the common workflow and specific experiment command classes that implement the five core experiment types from the paper.

The attack generation logic remains identical at the string level but is now better organized into focused modules. Prompt injection attacks still insert system message overrides into product descriptions. Discreditation attacks still add warnings about competitors. Persuasion attacks still include emotional appeals. The exact text patterns match those documented in the paper and reproduced in the original implementation. The refactoring simply moved these generation functions from scattered locations into a centralized attacks package, improving discoverability and maintainability without altering any attack text or injection logic.

EXPERIMENTAL WORKFLOW CHANGES
===============================================================================

The way experiments are configured and executed has been significantly reorganized but the underlying experimental protocols remain faithful to the paper's methodology. Previously, experiments were run by calling standalone functions with numerous parameters passed as arguments. Now, experiments are defined as configuration objects that capture all parameters in a structured, validated format, then executed through an experiment runner that orchestrates the workflow. This shift from procedural to object-oriented experiment design makes no changes to what experiments measure or how trials are conducted, but it does make experiments easier to reproduce and compare.

Baseline experiments establish clean product rankings without any attacks present, exactly as they did in the original implementation. The workflow loads products from the dataset, populates the vector database with unmodified descriptions, runs the specified number of trials by querying the LLM ranking system, and collects ranking results. The configuration object now captures parameters like number of trials, product count, and random seed more explicitly than the original argument-based approach, but the actual trial execution logic is unchanged. The advantage for research reproducibility is that configuration objects can be serialized to JSON and shared alongside results, making it trivial to verify that experiments used identical parameters.

Single attack experiments measure individual attack effectiveness by comparing baseline rankings to rankings after attack injection. The refactored code follows the same protocol: generate baseline rankings, inject an attack into one product's description, repopulate the vector database with the attacked description, rerun ranking queries, and measure whether the attacked product moved to position one. The success rate calculation uses the same formula, the same trial sampling procedure, and the same statistical aggregation. The modular structure simply separates attack generation from database population from ranking execution from results analysis, making each stage independently testable and easier to modify without introducing bugs.

Prisoner's dilemma experiments test what happens when multiple attackers compete by injecting attacks into multiple products simultaneously. The refactored implementation maintains the exact same experimental design where attacks are injected into a specified number of products, all products are reranked together, and success rates are measured both individually and collectively. The finding that collective attack success degrades when everyone attacks remains reproducible because the underlying ranking dynamics are unchanged. The refactored code simply makes it easier to vary the number of attackers or attack distribution patterns through configuration rather than code modification.

Positional bias experiments measure whether attack position within the retrieval context affects success rates. The original finding that attacks are more effective at the end of context windows is still observable in the refactored code because the retrieval ordering and LLM prompt construction are identical. Products are retrieved in the same order based on vector similarity, attacks are injected at the same positions, and the LLM sees the same prompt structure. The modular pipeline architecture makes it slightly easier to experiment with different position configurations, but default behavior exactly matches the original experimental design.

ARCHITECTURAL AND LOGICAL CHANGES
===============================================================================

The architectural transformation from monolithic to modular structure fundamentally improves code quality without altering research logic. The original codebase concentrated all functionality into four large files: one for experiments, one for the RAG system, one for analysis, and one for evaluation. Each file mixed multiple concerns, making it difficult to understand, test, or modify any single aspect of the system. The refactored architecture decomposes these files into twenty-five focused modules organized into packages, with each module responsible for a single well-defined aspect of the system.

The experiments package exemplifies this improved separation of concerns. The base module defines abstract experiment interfaces and data structures. The runner module orchestrates experiment execution with progress tracking and error handling. The commands module implements the five specific experiment types as independent classes. The factory module handles experiment creation from configuration. The results module manages result aggregation and persistence. This separation means changes to one experiment type cannot accidentally break others, new experiment types can be added without modifying existing code, and each component can be tested in isolation.

The RAG package similarly separates retrieval from generation from pipeline orchestration. The retriever module handles vector search strategies, making it easy to experiment with different similarity metrics or retrieval algorithms. The generator module handles LLM interaction, isolating provider-specific details and making it straightforward to swap between AWS Bedrock, OpenAI, or Anthropic models. The pipeline module combines retrieval and generation with observability hooks that provide complete transparency into what documents were retrieved, what prompts were sent to the LLM, and what rankings were produced. This glass-box approach to transparency was always a goal of the research but is now better supported by the architecture.

The design patterns applied throughout the refactored code establish consistent interfaces and extension points. The Template Method pattern in experiment classes ensures all experiments follow the same setup, execute, analyze, cleanup workflow. The Strategy pattern in retrieval and generation makes components pluggable without requiring inheritance. The Factory pattern centralizes object creation, ensuring consistent initialization. The Observer pattern enables progress tracking and logging without coupling experiments to specific monitoring systems. These patterns are standard software engineering practices that improve code quality without changing research methodology.

The testing strategy embedded in the refactored architecture provides confidence that changes do not introduce regressions. Unit tests verify individual functions and classes in isolation. Integration tests confirm that components work together correctly. Performance tests ensure that refactoring did not degrade efficiency. The original code had minimal testing, making it risky to modify anything for fear of breaking reproducibility. The comprehensive test suite in the refactored code enables confident modification and extension while maintaining reproducibility guarantees through automated verification.

Experiment execution code that calls standalone functions can be gradually migrated to use the new object-oriented interfaces. The migration path is designed to be incremental rather than requiring a complete rewrite.

The most common migration task involves updating import statements to use the new package structure. Code that previously imported from a monolithic experiments module now imports from the experiments package submodules. For example, experiment configuration that was previously accessed through a top-level function now comes from the experiments.base module. The changes are mechanical and can be performed with simple find-and-replace operations. The backward compatibility wrappers ensure that code continues to work during migration, allowing teams to update modules one at a time rather than requiring a simultaneous conversion.

Teams can update to the new format gradually, with some datasets remaining in the old format while others adopt the new structure. The loader's format detection eliminates the need for manual format specification or conditional logic based on dataset version.

Experiment configuration migrates from function arguments to configuration objects through a straightforward transformation. Where the original code passed numerous parameters to experiment functions, the refactored code creates configuration objects capturing those same parameters in a structured format. The advantage is that configurations can be saved, loaded, shared, and verified more easily than parameter lists. The migration involves grouping related parameters into configuration constructors, which makes experiment setup more explicit and easier to validate. Most teams find that the configuration object approach actually simplifies their experiment scripts once the initial migration is complete.

TECHNICAL DETAILS: KEY ALGORITHMIC PRESERVATION
===============================================================================

The positional bias experiment deserves particular attention because its implementation underwent the most significant structural refactoring while maintaining experimental fidelity. In the original code, attacks were injected by modifying product descriptions in place before the entire catalog was vectorized and stored in the database. The refactored approach injects attacks during document preparation but keeps the injection timing and embedding process identical. Products are still described with their original content in the vector database, with attack text appended at the description string level. The LLM still sees products in the same order based on vector similarity, and attacks still appear at the same positions within the description text.

The key insight is that attack position refers to the position within the LLM's prompt context window, not the position within the vector database. The retrieval process ranks documents by similarity and returns the top K matches. These matches are then formatted into a prompt that presents each product with its full description including any injected attack text. An attack at position three means the attacked product appears as the third product in this formatted prompt. The refactored code maintains this position numbering scheme exactly, ensuring that positional bias findings remain directly comparable to the original results.

The vector embedding process for attack documents maintains the same properties as the original. Each product description, including any attack text, is embedded using the same Gemini embedding model with the same parameters. The embeddings capture the semantic content of the full description including attack text, meaning that attacked products may retrieve differently than clean products based on the attack content. This retrieval behavior is part of the attack mechanism and is preserved identically in the refactored code. The separation between clean vector embeddings and attacked prompts mentioned in some design documents refers to future possible experiments, not the current implementation, which matches the original approach.

The ranking mechanism's independence from dataset structure deserves emphasis for reproducibility concerns. The LLM ranking process operates on a flat list of retrieved products with their descriptions formatted into a specific prompt structure. This prompt structure is identical between original and refactored code. The fact that products are organized by category in the source file has no impact on this ranking prompt, because the category structure is flattened during retrieval. The LLM receives the same input format, processes it with the same prompt instructions, and produces rankings based on the same criteria. Category information is available as metadata but does not alter the core ranking logic unless explicitly incorporated into prompts, which neither the original nor refactored code does for the baseline experiments.

The multi-provider support introduced during refactoring maintains identical behavior across LLM providers for the same model. When experiments specify AWS Bedrock with LLaMA, the exact same LLaMA model is used as in the original code with identical parameters. When experiments specify Anthropic Claude or OpenAI GPT, these are new capabilities enabled by refactoring that allow cross-provider comparison studies. The provider abstraction ensures that model invocation, prompt formatting, and response parsing follow provider-specific conventions correctly. Temperature settings, top-p parameters, and other generation controls maintain their original values to ensure reproducible behavior.
